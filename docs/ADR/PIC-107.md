# PIC-107: Restauração da Espera Reativa via Polling Node.js (Anti-Hang SSRS)

## Status
Aceito

## Contexto
Durante o desenvolvimento e testes do scraper de relatórios do SSRS no Conexão Educação (PIC-25/PIC-13), tentamos mover a lógica de polling (`setInterval`) da função `waitAspNetReady` para dentro do contexto do `BrowserWindow` (Chromium).
O objetivo era centralizar a espera do lado do cliente, encapsulando-a numa Promise única injetada via `executeJavaScript`.

No entanto, essa abordagem falhou catastroficamente:
1. **SSRS Infinite Loop (UpdatePanel):** Ao alterar opções como o "Semestre" para 0, o SSRS entrava em um loop infinito de `onload` de iFrames invisíveis que não paravam de recarregar.
2. **Timer Cancellation (ASP.NET WebForms):** A classe `Sys.WebForms.PageRequestManager` do ASP.NET destrói rotineiramente todos os timers (`setTimeout`/`setInterval`) para prevenir vazamentos de memória durante partial postbacks (`UpdatePanel`).
3. **Throttling de Timers no Electron:** O `BrowserWindow` estava rodando em background (`show: false`), o que acionava a suspensão de timers (throttling) do Chromium (reduzindo a execução para 1 vez por minuto).

Como resultado, o timer interno parava de executar, a Promise injetada nunca era resolvida e o processo no Node.js ficava aguardando eternamente (Hang completo do scraper).

## Decisão
1. **Reverter a arquitetura de espera:** Movemos o loop de polling de volta para o processo Node.js (função `waitAspNetReady` restaurada ao formato primitivo).
2. O Node.js agora despacha chamadas repetidas de `executeJavaScript` (a cada 500ms) para ler a variável global do `Sys.WebForms`.
3. Essa abordagem é 100% imune:
   - Ao congelamento do renderer por eventuais falhas do WebForms.
   - À destruição de timers internos (já que a injeção é ad-hoc, a cada iteração).
   - Ao throttling de background do Chromium (Node.js não é throttled).
4. O `waitAspNetReady` continua suportando `readyCondition` para aguardar que um elemento específico (dropdown) atenda aos critérios esperados, sem depender de mutações complexas em DOM.

## Consequências
- A robustez do scraping volta ao nível aceitável, não sofrendo hangings por timeout silencioso.
- A função foi corrigida (após um tropeço de syntax error e falta de retorno).
- A sincronização agora lida apropriadamente com a falha catastrófica de carregamento inicial (retornando as promessas corretamente).
