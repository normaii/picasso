# PIC-107: Restauração da Espera Reativa via Polling Node.js (Anti-Hang SSRS)

## Status
Aceito

## Contexto
Durante o desenvolvimento e testes do scraper de relatórios do SSRS no Conexão Educação (PIC-25/PIC-13), tentamos mover a lógica de polling e sincronização (via `MutationObserver` e `setInterval`) para dentro do contexto do `BrowserWindow` (Chromium).
O objetivo era centralizar a espera do lado do cliente, encapsulando-a numa `Promise` única injetada via `executeJavaScript` no passo de `WAIT_IFRAME_REPORT` e na troca de semestres.

No entanto, essa abordagem falhou catastroficamente gerando congelamentos (hangs) silenciosos que duravam até o timeout do script:
1. **O Gatilho Oculto do SSRS:** Ações de interface que parecem assíncronas (como clicar no botão "View Report") frequentemente disparam um **Full Postback** (submissão de formulário completa) no ASP.NET, em vez de uma mera requisição AJAX via `UpdatePanel`.
2. **Promessas Órfãs:** Quando ocorre a navegação da página inteira (Full Postback), o Chromium destrói **instantaneamente** todo o contexto JavaScript anterior da página. Consequentemente, a `Promise` injetada morre silenciosamente, sem nunca chamar `resolve()` nem `reject()`.
3. **Deadlock no Node.js:** O processo principal do Electron (Node.js) ficava parado aguardando a Promise morta. Sem resposta e sem timeout reativo (pois o próprio timer estava dentro do contexto destruído), o sistema congelava.
4. **Timer Cancellation (ASP.NET WebForms):** A classe `Sys.WebForms.PageRequestManager` também destrói rotineiramente todos os timers para prevenir vazamentos durante os partial postbacks que realmente ocorrem.

## Decisão
1. **Remoção Total da Injeção de Promises:** Movemos todo e qualquer loop de espera (`while`) para o lado do processo do **Node.js**. 
2. O Node.js agora despacha scripts curtos (via `executeJavaScript`) que rodam e retornam instantaneamente a cada 1 segundo.
3. Se a página estiver no meio de um *reload*, a chamada falha com reject na interface do Electron, o bloco `catch` do Node engole o erro (`waiting`), aguarda mais um segundo e tenta novamente na nova página carregada.
4. Essa abordagem é 100% imune a reloads completos da página, garantindo que o fluxo não trave em Promessas órfãs.

## Consequências
- Fim dos congelamentos silenciosos: se a página recarregar, o polling do Node.js sobrevive intacto.
- Remoção do `MutationObserver` excessivamente sensível em prol de verificações puras e previsíveis baseadas no estado real do DOM final (como a presença de opções na caixa de listagem).
- Processamento sequencial do Scraper (SSRS -> Iframe -> Table Extraction) atinge os 100% de estabilidade esperados para o PIC-25.
